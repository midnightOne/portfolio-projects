### Session continuity & voice UX

| # | St | Decision |
|---|---|---|
| D49 | 🔶 | **Resumable conversations with session legs (owner, 2026-07-02).** A *logical conversation* (`AIConversation`) may span multiple *provider sessions* ("legs"). The canonical store holds everything needed to (a) resume after any disruption — on the same or a **different** provider/model — and (b) fully reconstruct the conversation for admin review after the fact: turn history, tool-call traces (args + results), injected-context state, and a **latest-state snapshot** (active instructions, tool set, model alias, later D47 node ID). Disruptions are recorded **in the conversation history itself** as marker events (`session_disruption` with issue type + diagnostics, `session_resumed` with the new leg's provider/model), so a failed-and-recovered conversation is debuggable without the owner having been present. Resume never restores provider-side memory — the new leg is *briefed* by the harness from ground truth (state-ownership principle). Consequence: recovery-resume and deliberate mid-conversation provider/model switch are **one code path** with different triggers; it must be heavily tested (verification live-fire drill). |
| D50 | 🔶 | **Pre-recorded voice assets (owner, 2026-07-02; Phase 4 polish, with the voice work).** A small library of voice-matched audio clips played by the **client** at known moments: (a) latency fillers ("let me check…") when a server tool/MCP call exceeds a threshold — small rotating pool, context-tagged, cut off instantly when the model starts speaking or the user barges in; (b) **connection-state audio** ("sorry, connection issues — re-establishing…") played entirely client-side while D49 disconnect/resume runs, i.e., precisely when no model exists to speak; (c) optional session-mint greeting to mask cold-start. Clips are keyed by (voice, phrase), regenerated via the provider's TTS when the configured voice changes, and **every playback is logged as a D49 history event** so admin replay shows what the visitor actually heard (client clip vs model speech — critical for honest debugging). The D47 engine may later attach node-specific filler sets; the base feature is engine-independent. |
| D51 | 🔶 | **Conversation mode is user-intent-driven (owner, 2026-07-03).** The system tracks the *mode the visitor wants* — voice or text — as explicit state, **decoupled from device capability** (mic present/permitted). **Text-only is a first-class mode served by the reasoning/chat adapter family (D39; cascade brain per D45), NOT the realtime voice model** — different model, no audio output. Rules: (a) user wants text → text, even when a mic is available and permitted; (b) user wants voice but has no mic/permission → help them grant it, and if a mid-session upgrade isn't possible (D52 spike), start the text (reasoning) session and tell them to allow the mic and open a voice session; (c) the pill MUST disambiguate intent — never infer "voice" from a typed message (the bug observed 2026-07-03: typing produced a spoken realtime answer). Spec home: `ai-assistant`. |
| D52 | 🔶 | **Mic-less session start + permission UX (implemented 2026-07-03, interim).** The realtime adapter can start a session with no microphone (silent WebRTC input track — no `getUserMedia`, no permission prompt), enabling text input and automated e2e drivers. On a voice request without mic the pill offers **enable microphone** vs **stay text-only**; on browser-denied mic it falls back to text-only with **retry**. `startAudioInput()` upgrades a text-only session to mic by reconnecting (permission probed first so a denial preserves the text session). **Interim gap (superseded by D51):** a text-only session today still runs on the *realtime* model and speaks its answer; target routes text-only through the reasoning adapter. **Open spike:** can one native realtime session toggle mic on/off *without* reconnecting (create mic-less, stream text via the voice endpoint, later attach a live mic track in-session)? If yes, drop the reconnect upgrade; if no, D51(b) stands. |
| D53 | 🔶 | **Dev-only voice e2e via synthesized-audio input (owner, 2026-07-03; `verification` spec).** A development/test-only adapter/plugin that feeds **TTS-generated audio into an emulated microphone track**, so an automated agent with no human mic can exercise the *real* native-voice path end-to-end (mic track → provider STT → model → TTS out), not just text. Distinct from `FakeVoiceAdapter` (D46/Req 3, which bypasses the provider): this drives the **real provider** with synthetic speech. Dev/test only (never production), selected via `AI_FAKE_MODE`/env. Lets the agent validate voice-mode behavior and the D51 mode state machine without speaking. |
| D54 | ✅ | **Fresh-init migration baseline (owner, 2026-07-03; done same day).** Migration history collapsed to one `20260703220000_init` (schema.prisma is source of truth). Prisma's generated init already emits `CREATE EXTENSION IF NOT EXISTS "vector"` (extension is automatic); the sole hand-patch is the HNSW index (Prisma emits btree). Verified from an empty DB: clean apply, zero drift, extension + HNSW present. `npm run db:reset` (migrate reset + `prisma.seed` hook + fixture) re-provisions and reseeds in one command — retires the migration-ordering / `db push`-drift bug class from Phase 0. |
| D55 | 🔶 | **Unified passive-context pipeline — the context buffer (owner, 2026-07-03; implement with Phase 4 voice work / D47 prep).** Passive context provision is fragmenting across sources: per-UI-state (NAV_CONTEXT, exists), per-graph-state (D47), per-user-query (D41(d) classifier), possibly a watchdog LLM. **Unify at the pipeline level, not the function level:** all sources publish keyed context items into one **async per-conversation buffer** (last-write-wins per source key, TTL, token-budgeted merge); one injector flushes the diff into the model's context **at turn end** via the adapter's `updateSession` primitive (the D47(d) seam). This generalizes the proven NAV_CONTEXT replace-don't-append mechanics. **Race contract (accepted):** reactive sources (query classifier, watchdog) are inherently one turn behind — the model may answer turn N un-augmented and be corrected at turn N+1; do NOT make them synchronous/inline (latency). Mitigate by preferring *predictive* sources (graph state entry, UI state) that push before the question is asked. Every buffer flush is a D49 history event so replay shows what the model knew and when. Watchdog reframing (assistant judgment, owner-requested): as a *retrieval* source it is dominated by the classifier (cheaper) and the graph (deterministic); its durable niche is *supervision* (derailment detection/QA) writing into the same buffer — integrate as one more source, or defer. Cascade voice (D45) gets per-turn injection trivially. Spec home: `ai-assistant`. |

| D56 | 🔶 | **Debug surfaces exercise the production code path — always (owner, 2026-07-07; generalizes D21).** Admin debug/test surfaces must run the same server pipeline, providers, tools, and persistence as the live visitor experience — never a parallel implementation, simplified fork, or synthetic data source. "What the owner debugs" and "what the visitor gets" are the same code; only presentation (extra telemetry rendering, `_debug` envelope display, admin gating) may differ. A debug surface that drifts from production is worse than none: it certifies behavior that doesn't exist. Applies to current surfaces (`/admin/ai/debug` → `/api/ai/chat`; `/admin/ai/voice-debug` → production provider) and binds all future ones. |
| D57 | 🔶 | **Standing mock policy: found mocks are removed, documented, and replaced with real functionality (owner, 2026-07-07; extends D26/D42 from a one-time purge to a standing rule).** Whenever a mock/stub/fabricated-data path is discovered anywhere in the codebase — at any phase, in any spec's territory: (1) it is **removed** (never quietly left in place); (2) the finding is **documented** (owning spec ledger + the phase's execution notes: what was fake, who consumed it, what it silently broke); (3) it is **replaced with proper functionality** — either implemented immediately or filed as an explicit prioritized task with a NOT-IMPLEMENTED annotation on the affected requirement (pattern set by the `/api/ai/conversation/log` stub → Req 9.1 annotation → task 2b). No route ships fabricated data; no requirement silently rests on a stub. |
| D58 | 🔶 | **Unified, modality-labeled conversation storage (owner, 2026-07-07).** ONE conversation store and ONE text-based write pipeline (`conversation-history-manager`) regardless of modality — voice turns arrive as transcriptions and flow through the same pipeline as typed text. Every message carries a **per-message modality label**: `voice` (transcription of spoken audio — applies to ALL voice transcriptions, user and assistant alike) or `text` (typed/rendered text). Labels are per message, not per conversation or per turn-pair, because input and output modality may differ within one exchange and visitors may interleave freely: text-in→spoken-answer, voice-in→text-answer, and full multimodal interchange are all intended UX (the mixed-modality *functionality* may land as deferred tasks, but the **storage schema supports it now** — no second migration when it arrives). Audio itself is NEVER stored in the conversation store: if debug audio is ever captured, it is uploaded as a separate file asset (`media` domain) and referenced from the message. `hybrid` describes a conversation/session, never a message label. Spec home: `ai-assistant` (task 2b writes, D49 5b legs on top). |

## Future platform (owner, 2026-07-02 — backlog with binding seams)

| # | St | Decision |

| D47 | 🧊 | **Node-graph conversation templating engine** (post-roadmap; outline in [`../_backlog/conversation-engine.md`](../_backlog/conversation-engine.md)). Admin-editable node graph: nodes bundle guidance/preferred-answer material + context set + tool allowlist + model alias; edges are transition/fork conditions that can **purge and switch context and model** mid-conversation. | D48 | 🧊 | **Modular agentic platform — the agent subsystem is a future standalone showcase/product** (outline in [`../_backlog/agentic-platform.md`](../_backlog/agentic-platform.md)). Target modules, each usable without the others: **agent-core** (adapters: native voice / cascade / reasoning; tool registry; session + logging contracts; later the D47 engine), **rag-core** (chunking/embedding/search behind a content-source interface; MCP exposure), **ui-navigator** (SemanticIDRegistry + UIManager + `ui_intent` — an optional capability), **capability plugins** (e.g., job/CV analysis — optional tools discovered via the registry, never built-in). Boundary litmus test: *"would the phone agent need it?"* **Constraints binding NOW:** (a) dependency direction — `src/lib/{ai,voice,navigation,content}` never import from `src/app/**` or portfolio components; portfolio-specific tools/config register **into** the registries from outside; (b) no portfolio-specific strings/prompts hardcoded in core libs (assembled from config/DB); (c) F-I-D and UI navigation stay optional — every adapter must run a useful session with zero context injections and no client tools; (d) content ingestion consumes a **content-source interface** (the Tiptap reader is one adapter of it), so a foreign DB is a new adapter, not a rewrite; (e) no premature package extraction — folder discipline now, `packages/` split only when a second consumer exists. |
