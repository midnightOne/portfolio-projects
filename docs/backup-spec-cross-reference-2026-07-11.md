**Purpose:** Identify which backup tasks that were still unchecked were subsequently delivered, deliberately replaced, or remain unfinished.

## How to read this report

This is a ledger-to-ledger reconciliation, not a new source-code audit. “Completed” means the active task ledger records a successor as completed and, where noted, says it was verified. “Partially complete” means that a meaningful successor exists but its remaining acceptance work is explicitly open. “Superseded” means a later architecture decision intentionally replaced the original task; it is not a request to rebuild the obsolete design.

The old backup had 201 unchecked checkbox lines, but that number is misleading: `client-side-ai/tasks.md` contains repeated task numbers, nested planning variants, and incompatible end-state assumptions. The refactor was justified. The active tree separates that material into `access-and-cost`, `ai-assistant`, `ai-admin`, `mcp-server`, `semantic-content`, `verification`, and `conversation-engine`, where ownership is substantially clearer.

## Executive conclusion

Most of the important pre-refactor capability plan has now been delivered or deliberately redesigned:

- The shared tool chain, public text access, rate limits, spend ledger/watchdog, provider adapters, model aliases, semantic retrieval, MCP server, and conversation-engine core are recorded as completed.
- The old “ElevenLabs conversational agent” path was correctly replaced by native OpenAI/Gemini voice plus the cascade architecture, where ElevenLabs is an STT/TTS engine instead of the agent orchestrator.
- The most important genuinely unfinished work is now much narrower: verification automation, semantic-operation reliability, a few voice/runtime correctness gaps, and deployment activation.

The project should not reopen old broad “AI system” or “client-side AI” plans. The correct next action is to close the active, named gaps with the current architecture intact.

## Work that was added after the backup and should remain in the plan

The refactor did more than reorganize old work. It introduced important responsibilities that the backup did not adequately capture:

- A fail-closed AI gateway, unified ledger, spend watchdog, public-chat defense, and MCP rate bucket.
- Alias-based provider/model administration and a three-provider reasoning layer.
- An external, read-only MCP server with visibility filtering and hardening checks.
- A durable conversation graph with graph versions, editor, traversal, tool scoping, chips, slots, leads, replay, coverage, memory, and safety tripwires.
- Privacy-aware resume mechanics that distinguish same-device continuity from a new device/browser.
- A real verification posture: fake providers are valid in deterministic tests, live-fire is deliberate and metered, and production paths must not enable fake mode.

These are not “extra polish.” They are the architecture that makes the completed backup capabilities safe to operate.

## Genuine remaining work, ordered by value

1. **Make semantic operations reliable.** Fix `scope:'all'` persistence, make queue state independent of SSE subscription, and implement cumulative parent T2 summaries with fixture coverage. Do not expose bulk operations as trustworthy until then.
2. **Close the verification loop.** Deliver `FakeVoiceAdapter`, unified telemetry lookup by `requestId`, Playwright paths, `check:models`, and repeatable live-fire scripts. Activate CI only after the owner authorizes the push.
3. **Complete graph verification before treating the engine as finished.** Seed the real graph, author golden scenarios, run fake scenario checks, and perform the documented multi-runtime live-fire drill.
4. **Address the highest-leverage voice/runtime gaps.** UI-state pull, system-prompt diet, Gemini Live usage metering, transcript/clip feedback diagnosis, and the decision on Firefox fallback/provider lifetime are all better investments than additional provider features.
5. **Curate documentation.** Keep the new specs authoritative, archive old guides that describe removed endpoints/configuration, and publish one current operator path for environment, access/spend, verification, and incident recovery.

## What I would change in the planning process

- Keep the backup only as a historical input. Do not copy its checkbox state into current ledgers.
- For every archive-to-current migration, add a short “disposition table” like this report: **completed**, **renamed**, **superseded with reason**, or **carried forward to a named task**. This makes deliberate non-work visible.
- Avoid umbrella tasks such as “complete AI system” or “production verification.” Require a concrete owner, acceptance command/drill, and data boundary.
- Treat UI claims and operational claims differently. “The panel exists” is not “the panel safely drives the real system”; require a browser test for the latter.
- Preserve the current rule that fake mode is test infrastructure, never production behavior. The backup’s “no mock” wording would otherwise make the system harder—not safer—to verify.
